# VIBLOC 개발 현황·목표·로드맵 총정리

> 본 문서는 2026년 4월 기준으로, 레포지토리 실제 구성·대화에서 정리된 제품 방향·진행도·향후 작업을 **한 파일에서** 추적하기 위한 도큐멘터리형 기록이다.  
> 제품의 **원천 스펙·비주얼 법칙·페이즈 정의**는 루트 **`CLAUDE.md`** 가 우선이며, 본 문서와 충돌 시 **`CLAUDE.md`** 를 따른다.

---

## 서문: 이 프로젝트가 말하는 이야기

**VIBLOC(바이블록)**은 *Vibe + Block*을 합친 이름으로, **실제 도시의 블록(건물·거리)** 위에 **음악적 바이브(취향·장르·곡)** 를 겹쳐 보는 웹 경험을 목표로 한다. 지도는 단순한 배경이 아니라 **입체적인 3D 캔버스**이고, 사용자의 태그와 시간이 쌓이면 **건물과 동네의 색·분위기가 변하는** "살아 있는 음악 지도"에 가깝다.

현재 코드베이스는 그 **시각적·공간적 골격(프론트 3D + 정적 도시 데이터 + 클라이언트 음악 파이프)** 까지는 상당 부분 갖추었으나, **계정·서버·데이터베이스에 의존하는 소셜·개인화 기능**은 아직 시작 단계에 있다. 이 문서는 그 **간극**을 기록하고, 앞으로 무엇을 **만들어야 하는지**를 순서와 책임 영역별로 풀어 쓴다.

## 제1부: 개발 목표 및 방향성

### 1.1 비전 (한 문장)

**실제 도시 3D 맵 위에서 음악 취향을 건물·공간과 연결하고, 개인과 집단의 태그가 쌓이며 도시가 음악적으로 "물드는" 소셜·시각화 웹 서비스**를 지향한다.

### 1.2 사용자 여정 (목표 상태)

1. **첫 방문** — 브라우저로 들어오면 **랜딩(홈)** 에서 "이 사이트가 무엇인지" 짧게 이해한다. (간판 역할)
2. **탐색** — **맵으로 들어가기**를 누르면 3D 도시가 열리고, **비회원**도 **맵 둘러보기**는 가능하다.
3. **깊이 참여** — **회원**은 건물을 눌렀을 때 열리는 **옆 패널**에서 다른 사용자의 추천·댓글·좋아요를 보며 상호작용한다.
4. **표현** — 사용자는 **특정 건물·거리 맥락**에 어울리는 곡을 **직접 추천**할 수 있고, 다른 사람은 그 추천에 **좋아요**를 누를 수 있다. **댓글**은 좋아요와 무관하게 달 수 있다.
5. **발견** — **AI** 가 상황(건물·동네·시간·날씨·기존 태그 등)에 맞춰 **곡 후보·검색 힌트**를 제안할 수 있다 (실제 재생은 기존과 같이 **iTunes 등 안전한 소스**에 맡긴다).
6. **하이라이트** — 건물 패널 **상단**에는 **좋아요가 많은 플레이리스트 Top 3** 정도가 **작성자 프로필**과 함께 노출되고, **축하·강조 연출**(예: 폭죽 애니메이션)을 검토할 수 있다.
7. **나만의 공간** — **마이페이지**에서 **받은 좋아요**, **알림 설정**, **플레이리스트 관리**를 한다.

### 1.3 기술 방향 (원칙)

| 축 | 방향 |
|----|------|
| **프론트** | React, TypeScript, Vite 유지. 3D는 React Three Fiber 생태계. 상태는 Zustand 등. |
| **백엔드** | **MySQL** 을 쓸 계획이면, REST(또는 선호하는 API 스타일) + **인증(JWT 등)** + **서버에서만 보관하는 비밀키**(AI, 선택적 외부 API). |
| **데이터** | 도시 지오메트리·OSM 파생 JSON은 계속 **정적 `public/data`** 로 제공 가능. **사용자 생성 콘텐츠**는 DB에만 둔다. |
| **보안** | 검색 쿼리 등 민감 흐름은 `docs/SECURITY.md` 철학과 맞게 — **불필요한 제3자 런타임 호출 최소화**, `.env` 는 Git에 올리지 않는다. |

### 1.4 `CLAUDE.md` 와의 관계

루트 **`CLAUDE.md`** 에는 이미 **디자인 원칙(SSAO, 팔레트, iTunes 1차 음원 소스 등)** 과 **Phase 1~4** 가 정의되어 있다. 본 문서의 "소셜·마이페이지·AI" 는 **`CLAUDE.md` Phase 2~3** 의 확장 서술에 해당한다. 구현 우선순위를 정할 때는 **기존 Phase 문구**와 **본 문서의 사용자 스토리**를 함께 본다.

## 제2부: 현재 진행 상황

### 2.1 레포지토리·실행 환경

- **의존성 관리:** `package.json` + `package-lock.json` 기준 **npm** 이 주 워크플로. `bun.lock` 이 공존할 수 있으나, 팀·개인은 **하나로 통일**하는 것이 유지보수에 유리하다.
- **개발 서버:** `npm run dev` 또는 `npm start` → Vite (기본 포트 5173 전후).
- **빌드:** `npm run build` 는 `tsc -b` 후 `vite build` 를 수행한다. 과거 기준 **엄격한 TS 옵션**으로 인해 **미사용 변수 등**에서 빌드가 막힐 수 있어, **배포 전 점검**이 필요할 수 있다.
- **Git:** 프로젝트 폴더 단위로 저장소를 두는 것이 바람직하며(상위 홈 디렉터리 전체가 Git 루트가 되면 IDE·성능 이슈가 생길 수 있음), 원격 예시로 **GitHub `sella45/vibloc`** 가 언급된 바 있다.

### 2.2 프론트엔드 — 이미 갖춘 것

| 영역 | 내용 |
|------|------|
| **스택** | React 19, TypeScript, Vite, Tailwind CSS v4, Framer Motion |
| **3D** | React Three Fiber, @react-three/drei, postprocessing, n8ao(SSAO), three, 3d-tiles-renderer |
| **상태** | Zustand (건물·시간·날씨 등) |
| **도시 데이터** | `public/data` 내 다수 JSON — 도시별 건물·지형·POI·위키 보강 등 |
| **지오·검색** | OSM 로더, 지오코딩, Plus Code, 한·일 주소 보조, 검색 랭킹 등 (`src/lib/geo` 등) |
| **건물 표현** | 태그·장르에 따른 색·상태 (`tasteEngine` 등), 캔버스 쪽 컴포넌트 다수 |
| **UI** | 검색바, 나침반, 시간 슬라이더, 다국어(i18n), 스트리트뷰(키 있을 때)·Wikimedia/OSM 폴백, 빌딩 패널, 음악 관련 UI(추천 리스트, 플레이리스트 컴포저, 프리뷰 플레이어 등) |
| **음악(클라이언트)** | iTunes Search API 연동 모듈, 장르 정규화·색 매핑, 추천 엔진·플레이리스트 훅 — **대부분 로컬/세션 단위**, **다른 사용자와 공유되는 서버 저장소는 없음** |
| **폴더 구조** | `docs/` 문서, `scripts/data/` 데이터 파이프라인, `src/lib` 도메인 분리(geo, streetview, scene, app, music, weather) 등 정리됨 |

### 2.3 백엔드·데이터베이스 — 아직 없는 것

- **MySQL 인스턴스·스키마·마이그레이션** — 문서상 계획만 있고, 레포에 **서버 코드·ORM 설정·테이블 DDL** 은 아직 없다.
- **인증** — 로그인·회원가입·세션·토큰 발급 API 없음.
- **소셜 데이터** — 댓글·좋아요·공개 플레이리스트·알림을 저장하는 **영구 저장소** 없음.
- **AI 프록시** — API 키를 숨기고 모델을 호출하는 **서버 엔드포인트** 없음.

### 2.4 제품 관점 — 화면 단위 갭

| 화면·기능 | 현재 |
|-----------|------|
| **랜딩(홈) — 서비스 설명 간판** | **없음.** 진입 시 곧바로 맵 중심 앱에 가깝다. **라우터로 `/` 와 `/map` 분리 필요.** |
| **로그인·회원가입·프로필** | **없음.** |
| **비회원 맵 / 회원만 댓글** | **정책만 구상.** 구현 없음. |
| **건물 패널 — 타 유저 추천·좋아요·댓글·Top3 플레이리스트** | **없음.** 패널은 주소·지도·음악 UI 등 **클라이언트 기능** 위주. |
| **마이페이지** | **없음.** |
| **알림** | **없음.** |

## 제3부: 해야 할 것 — 전체 목록 (역할별)

아래는 **중복을 허용하고** "빠뜨리지 않기" 위해 **화면·기능·인프라**를 나누어 적는다. 실제 스프린트에서는 **같은 항목을 하나의 이슈**로 묶어도 된다.

### 3.1 프론트엔드

1. **라우팅 도입** — `react-router-dom` 등으로 경로 분리.
2. **랜딩 페이지 (`/`)** — 서비스 한 줄 정의, 짧은 설명, **맵으로 이동** CTA, (선택) 로그인 링크 자리.
3. **맵 앱 라우트 (`/map` 등)** — 현재 메인 3D 앱을 이 경로로 옮기거나 래핑.
4. **인증 UI** — 로그인, 회원가입, 로그아웃, 비밀번호 재설정(선택).
5. **건물 패널 확장** — 탭 또는 섹션: 정보 / 커뮤니티 추천·좋아요 / (선택) AI / Top3 플레이리스트 영역.
6. **권한에 따른 UI** — 비회원: 댓글·일부 목록 숨김 또는 "로그인 후 확인"; 회원: 전체.
7. **마이페이지** — 플레이리스트 관리, 받은 좋아요 요약, 알림 on/off.
8. **Top3 연출** — 프로필 표시 + 폭죽 등 가벼운 애니메이션(성능·접근성 고려).
9. **API 클라이언트** — fetch/axios + 인증 헤더, 에러·로딩 처리.
10. **`npm run build` 안정화** — 배포를 막는 TS/린트 이슈 정리.

### 3.2 백엔드

1. **프로젝트 생성** — Node(Nest/Fastify/Express), Spring Boot 등 팀 스택 선택.
2. **MySQL 연결** — 커넥션 풀, 환경별 설정.
3. **마이그레이션** — Flyway, Liquibase, Prisma migrate 등으로 스키마 버전 관리.
4. **인증** — 회원가입·로그인, 비밀번호 해시(bcrypt 등), JWT 발급·검증 미들웨어.
5. **REST(또는 선택 API)** — 건물 식별자 규약(`city_key` + `osm_building_id` 등)에 맞춘 CRUD.
6. **비즈니스 규칙** — 좋아요 중복 방지, 본인만 수정·삭제, 비회원 읽기 범위.
7. **AI 프록시(선택 단계)** — 프롬프트·응답 캐시, rate limit, 비용 상한.
8. **파일 업로드(선택)** — 프로필 이미지 → 객체 스토리지 + URL 저장.
9. **알림 생성** — 좋아요 발생 시 `notifications` 행 삽입 등 (푸시·메일은 후순위).

### 3.3 데이터베이스 (MySQL) — 개념 ERD 요약

엔티티 관계는 다음과 같이 잡을 수 있다 (상세 컬럼은 별도 DDL로 정제).

- **users** — 계정
- **profiles** — 표시 이름, 아바타, 알림 설정 JSON 등 (users 와 1:1)
- **buildings** — 내부 surrogate `id`, `city_key` + `osm_building_id` 유니크
- **music_recommendations** — 건물에 유저가 올린 곡(iTunes 메타 등)
- **music_recommendation_likes** — 추천당 유저당 1좋아요 유니크
- **building_comments** — 건물 스레드; `related_recommendation_id` 로 특정 추천 아래 댓글도 가능
- **playlists** — 유저 소유; `building_id` nullable 로 "이 건물에 공개된 플레이리스트" 연동
- **playlist_tracks** — 플레이리스트 곡 순서·메타
- **playlist_likes** — 플레이리스트 좋아요 (Top3 집계용)
- **notifications** — 수신·읽음 처리 (1차 인앱)

선택: **ai_recommendation_cache** — building + context 해시별 응답 캐시.

### 3.4 인프라·운영

1. **호스팅** — API 서버, MySQL, (선택) Redis, 객체 스토리지.
2. **프론트 배포** — Vercel 등 + API 베이스 URL 환경 변수.
3. **CORS·HTTPS** 설정.
4. **관측** — 로그, 에러 트래킹(선택).
5. **백업·복구** — DB 정책.

### 3.5 문서·협업

1. 본 문서와 **`CLAUDE.md`** 동기화 (큰 방향 바뀔 때).
2. **API 명세** — OpenAPI/Swagger 또는 README 섹션.
3. **로컬 개발 가이드** — DB 띄우기, 시드 데이터, `.env` 키 목록.

VIBLOC은 이미 **"도시를 입체로 보여 주고, 음악을 건물과 연결하는"** 프론트의 설득력 있는 뼈대를 갖추었다. 다음 장은 **첫 화면에서의 약속(랜딩)** 과 **그 약속을 사람들이 함께 쌓아 올릴 수 있는 저장소(백엔드·MySQL)** 를 잇는 일이다. 이 문서는 그 길 위의 **체크리스트**로 쓰이고, 세부 설계가 굳어질수록 **DDL·API 명세**로 치환·갱신되면 된다.
